# Принципы
- Сервис НЕ ставит диагноз. Он использует готовое заключение ИИ-сервиса для навигации пациента
  и поддержки сотрудника клиники.
- Врач всегда в контуре: рекомендации доходят до пациента только после подтверждения врачом
  (исключение — призыв связаться с клиникой в неотложных кейсах, см. протокол).
- Отметки врача являются истиной для всего дальнейшего пути.
- Пациенту не показываются диагнозы и находки, только понятное объяснение дальнейшего маршрута.
- Уровень срочности "Неотложный" может понизить только врач, с указанием причины.

# Роли
- Врач — проверяет и подтверждает рекомендации ai-service.
- Оператор (администратор / контакт-центр / координатор) — работает с пациентами, которые
  не записались сами: звонит, записывает, фиксирует результат контакта.
- Руководитель — смотрит воронку конверсии и SLA (только чтение).
- Пациент — получает рекомендации и записывается через веб / приложение.

# Компоненты
- МИС/РИС — источник заключений, посещений, записей и свободных слотов (в MVP — mock).
- main-B2B — приём заключений, хранение кейсов, очередь проверки, таймеры follow-up, задачи оператору.
- ai-service — генерация рекомендаций, объяснений и уровня срочности. Каталог услуг и
  рекомендации Минздрава хранятся в нём.
- B2C сервис — уведомления пациента, граф здоровья, запись.
- Веб-интерфейсы: врача (очередь проверки), оператора (рабочий список), руководителя (дашборд).
- Сервис уведомлений — пуш, SMS, email (в MVP — mock с записью в лог).

# B2B путь (happy path)
1. Приходят данные пациента + медицинское заключение от ИИ-сервиса в main-B2B. Main сохраняет
   данные запроса и создаёт кейс маршрута (статус `draft`). Повторная отправка того же
   заключения не создаёт дубль (идемпотентность по ID исследования).
2. Main передаёт в ai-service то, что пришло изначально + имеющиеся данные пациента (текущие
   рекомендации, посещения и записи) + актуальные данные из МИС/РИС или через API (посещения
   и записи). ai-service генерирует список рекомендации с метками важности, которые врач после просмотрит.
   Выход ai-service для каждой рекомендации:
   - услуга из каталога клиники (или "услуга отсутствует в клинике");
   - краткое обоснование для врача: почему, зачем и на чём основана рекомендация
     (ссылка на рекомендации Минздрава);
   - понятный текст для пациента (без диагноза);
   - пометка, если пациент уже записан на эту услугу (такая рекомендация не дублируется).
   Для кейса в целом — уровень срочности: Норма / Плановый / Приоритетный / Неотложный.
3. Main добавляет кейс в очередь на проверку врачом (статус `in_review`). Порядок в очереди
   определяется срочностью от ai-service, внутри уровня — временем поступления.
   Кейсы "Неотложный" обрабатываются по отдельному протоколу (см. ниже).
   В рамках MVP реализуется веб-интерфейс со списком, где врач по каждой рекомендации выбирает:
   - крайне важна;
   - менее важна;
   - не нужна (с выбором причины: противопоказано / другое).
   Также врач может:
   - дописать свою рекомендацию;
   - изменить уровень срочности (понижение — только с причиной).
4. После того как врач отметил все рекомендации, кейс переходит в статус `confirmed`, информация
   возвращается в main-B2B и передаётся в B2C сервис. Отметки врача и причины отклонения
   сохраняются (в будущем — данные для улучшения ai-service).
5. Уведомление пациента. Стратегия зависит от срочности:
   | Срочность    | Уведомление пациенту                  | Follow-up, если нет записи                        |
   |--------------|---------------------------------------|---------------------------------------------------|
   | Неотложный   | см. протокол неотложных               | задача оператору сразу, SLA 1 час                 |
   | Приоритетный | пуш + SMS сразу                       | через 24 ч → задача оператору, SLA 4 часа         |
   | Плановый     | пуш сразу, напоминания на 3-й и 7-й день | через 7 дней → задача оператору, SLA 2 раб. дня |
   | Норма        | напоминание о плановом скрининге в срок | нет                                             |
   Кейс → `notified`. Если пациент записался сам (через B2C или по телефону, видно из МИС),
   таймер follow-up отменяется, кейс → `booked`.
6. Follow-up оператора. Если таймер истёк, main-B2B создаёт задачу в рабочем списке оператора.
   Оператор звонит, записывает или фиксирует результат (см. "Интерфейс оператора").
7. Закрытие кейса: `completed` — пациент пришёл на приём (факт берётся из МИС);
   `declined` — отказ с причиной; `unreachable` — не удалось связаться после всех попыток.

# Протокол неотложных кейсов
Цель: критическая находка не должна ждать в общей очереди. Ложная тревога стоит одного
лишнего звонка, пропуск — здоровья пациента.
Сервис дополняет существующий регламент клиники по критическим находкам, а не заменяет его:
дублирует сигнал, контролирует сроки и логирует все действия.
Подтверждение врачом и контакт с пациентом идут параллельно:
| Время           | Действие                                                                          |
|-----------------|-----------------------------------------------------------------------------------|
| T+0             | Кейс вверху очереди врача, красная подсветка, таймер SLA, браузерное уведомление со звуком. Оператору — задача "Срочно связаться". Пациенту — баннер "Врач просит срочно связаться с клиникой" с кнопкой звонка (без находки). |
| T+30 мин        | Врач не открыл кейс → эскалация дежурному врачу / заведующему.                    |
| T+1 ч           | Оператор не дозвонился → SMS "срочно свяжитесь с клиникой", повтор звонка каждые 15 мин. |
| T+2 ч           | Нет контакта → эскалация ответственному администратору.                          |
| Врач понизил уровень | Задача оператора пересчитывается по новому SLA или отменяется, причина — в лог. |
Оператор звонит по нейтральному скрипту: "По результатам исследования врач просит вас срочно
связаться с ним / приехать на консультацию", без озвучивания находки.

# Статусы кейса маршрута
draft → in_review → confirmed → notified → booked → completed
                                         ↘ declined / unreachable

Задача оператора — отдельная сущность со своим жизненным циклом (SLA, попытки, результат)
и статус кейса не меняет: в неотложном протоколе она создаётся, пока кейс ещё в `in_review`.

# Интерфейс оператора (MVP)
- Рабочий список задач: сортировка по срочности и дедлайну SLA, просроченные сверху.
- Карточка пациента: контакты, подтверждённые врачом рекомендации, текст для пациента,
  скрипт звонка (генерируется по подтверждённым рекомендациям, без диагноза), история касаний.
- Действия:
  - "Записал" — выбор слота из МИС, кейс → `booked`;
  - "Не дозвонился" — повтор через N часов, после 3 попыток SMS и эскалация;
  - "Перезвонить позже" — указать дату;
  - "Отказ" — причина: дорого / далеко / лечится в другой клинике / не считает нужным / другое.

# Дашборд руководителя (MVP)
- Воронка: заключения → рекомендации → подтверждено врачом → уведомлено → записались → пришли.
- Разрезы: срочность, модальность (КТ / РГ / ММГ), канал записи (сам в приложении / через оператора).
- SLA: доля задач врача и оператора, обработанных вовремя.
- Причины отказов.

# B2C путь (happy path)
1. Клиент заходит на веб-страницу (или переходит по deep link из уведомления сразу в нужную
   рекомендацию).
2. B2C сервис запрашивает данные о посещениях и записях из МИС/РИС или через API
   (актуализирует информацию).
3. На основе актуальных данных строит граф здоровья — понятную визуализацию.
   Граф строится на подтверждённых врачом рекомендациях и данных МИС/РИС.
   - Ноды: исследование → рекомендация → запись / визит.
   - Статусы нод: рекомендовано / записан / выполнено.
   - В нодах — понятный текст для пациента, без диагнозов и медицинских формулировок,
     которые могут напугать.
   - Если пациент уже записан на рекомендованную услугу, нода показывает "вы записаны"
     вместо кнопки записи. Так же можно перенести или отменить запись с указанием причины.
4. После просмотра графа и доп. информации юзер может быстро записаться к врачу прямо внутри ноды:
   B2C запрашивает свободные слоты из МИС, пациент выбирает слот, запись создаётся в МИС,
   кейс → `booked`, таймер follow-up отменяется.
   Если услуги нет в клинике, нода показывает рекомендацию обратиться к профильному
   специалисту и контакт клиники для консультации.

# Безопасность и регуляторика
- Персональные и медицинские данные (152-ФЗ, врачебная тайна по 323-ФЗ): деперсонализация
  данных перед передачей в LLM, LLM разворачивается on-prem или в российском контуре,
  внешние API для медданных не используются.
- Позиционирование: организационная навигация пациента с обязательным подтверждением врачом,
  а не самостоятельная постановка диагноза.
- Согласие пациента на получение уведомлений.
- Аудит-лог: кто, когда и что подтвердил, изменил, кому позвонил.
- Разграничение доступа по ролям (врач / оператор / руководитель / пациент).
- Версионирование каталога услуг и рекомендаций Минздрава: для каждой рекомендации
  известно, на основе какой версии она выдана.

# Интеграция
- Вход: вебхук от МИС/РИС о новом заключении или API main-B2B; формат по возможности
  HL7 FHIR (DiagnosticReport).
- Выход в МИС: запись на приём (Appointment), направление (ServiceRequest).
- Между main-B2B и ai-service: в MVP — синхронный HTTP-вызов из фонового воркера main-B2B
  (асинхронность обеспечивает очередь задач в Postgres); в проде — брокер сообщений
  с гарантией доставки.
- B2C встраивается в сайт клиники / личный кабинет / мобильное приложение (deep link на кейс).
- В MVP интеграция с МИС/РИС, SMS и пушами имитируется (mock).

# Скоуп MVP
Делаем:
- приём заключений через mock-МИС, main-B2B, ai-service;
- веб врача (очередь, отметки, правка текста, протокол неотложных с таймерами);
- веб оператора (рабочий список, карточка, действия);
- B2C веб (граф здоровья, запись в ноде);
- дашборд воронки;
- таймеры follow-up и эскалации.
Не делаем (мокаем или откладываем):
- реальную интеграцию с МИС/РИС;
- реальные SMS, пуши, звонки (только лог);
- уведомления врачу вне веб-интерфейса;
- мобильное приложение (только адаптивный веб).
