# b2b-service (main-B2B) API

Базовый адрес: `http://localhost:8080`. Общие соглашения, коды ответов и справочник значений — в [README](README.md).

b2b-service — модульный монолит из четырёх модулей. Модули не делят ни таблиц (у каждого своя схема Postgres), ни транзакций. Друг с другом они общаются только через публичные интерфейсы и события. Поэтому каждый модуль можно вынести в отдельный сервис, не меняя этот API.

| Модуль | Что владеет |
|---|---|
| `gateway` | Приём заключений из МИС, вызов ai-service, адаптер МИС для остальных модулей |
| `doctor` | Очередь и карточка врача, отметки, срочность, подтверждение, эскалация «кейс не открыт» |
| `care` | Маршрут после подтверждения: таймеры протокола, уведомления, задачи администратора, записи, план для b2c, дашборд |
| `system` | Бизнес-часы и демо |

Изменения из одного модуля доходят до другого событием за доли секунды. Например, план пациента и задачи администратора отражают подтверждение врачом не в том же ответе, а сразу после него.

## Приём заключения

`POST /api/v1/reports`

Регистрирует заключение в статусе `received` и ставит его на фоновую оценку ai-service. После оценки заключение становится `assessed`, а кейс появляется в очереди врача (`in_review`).

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `source_system` | string | да | Идентификатор МИС-источника |
| `study.id` | string | да | ID исследования в МИС; вместе с `source_system` — ключ идемпотентности |
| `study.modality` | `CT` \| `DX` \| `MG` | да | Модальность |
| `study.body_site` | string | нет | Область исследования |
| `study.performed_at` | RFC 3339 | да | Дата и время исследования |
| `conclusion` | string | да | Заключение ИИ по исследованию |
| `patient.id` | string | да | ID пациента в МИС |
| `patient.full_name` | string | да | ФИО |
| `patient.birth_date` | `YYYY-MM-DD` | да | Дата рождения |
| `patient.sex` | `male` \| `female` | да | Пол |
| `patient.phone` | string | нет | Телефон |
| `patient.email` | string | нет | Email |

```json
{
  "source_system": "mis-demo",
  "study": {
    "id": "MG-2026-0001",
    "modality": "MG",
    "body_site": "breast",
    "performed_at": "2026-10-03T09:00:00Z"
  },
  "conclusion": "Маммография обеих молочных желез. В верхне-наружном квадранте левой молочной железы образование неправильной формы 12 мм с нечёткими контурами. Заключение: BI-RADS 4.",
  "patient": {
    "id": "P-ANNA",
    "full_name": "Анна Смирнова",
    "birth_date": "1974-03-12",
    "sex": "female",
    "phone": "+79990000001",
    "email": "anna@example.com"
  }
}
```

Ответ:

```json
{ "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f", "status": "received" }
```

`status` — статус обработки заключения: `received` — ждёт оценки ai-service, `assessed` — оценено и передано врачу.

| Код | Когда |
|---|---|
| 201 | Кейс создан |
| 200 | Исследование уже принято с тем же содержимым; в ответе существующий кейс и его текущий статус. ФИО, дата рождения, пол и контакты пациента обновляются |
| 400 | Некорректный JSON; не заполнено обязательное поле; `modality` или `sex` вне списка; дата не в нужном формате |
| 409 | Исследование уже принято, но отличается пациент, модальность, область, дата исследования или текст заключения |

Повтор считается тем же исследованием, если совпадают `patient.id`, `modality`, `body_site`, `performed_at` и `conclusion`.

### Статус обработки заключения

`GET /api/v1/reports/{case_id}`

```json
{
  "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
  "study_id": "MG-2026-0001",
  "status": "assessed",
  "received_at": "2026-10-04T06:34:03.562141Z",
  "assessed_at": "2026-10-04T06:34:03.878396Z"
}
```

Если ai-service не ответил после всех попыток, заключение остаётся `received` с `assessed_at: null`, а врач кейса не видит. Сбой видно в логах.

| Код | Когда |
|---|---|
| 200 | Заключение найдено |
| 404 | Заключения нет или `case_id` не UUID |

## Карточка кейса

`GET /api/v1/cases/{id}`

Полные данные для врача, включая текст заключения и обоснования рекомендаций. Пациенту и администратору этот ответ не показывается. Кейс доступен с момента оценки ai-service. Пациент здесь псевдонимный: ID в МИС, дата рождения и пол, без ФИО и контактов.

```json
{
  "id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
  "patient_id": "cdf7735e-a6bc-4b28-9866-77c313076611",
  "source_system": "mis-demo",
  "study_id": "MG-2026-0001",
  "modality": "MG",
  "body_site": "breast",
  "performed_at": "2026-10-03T09:00:00Z",
  "conclusion": "Маммография обеих молочных желез. … Заключение: BI-RADS 4.",
  "status": "in_review",
  "urgency": "priority",
  "catalog_version": "2026.10",
  "guidelines_version": "2026.09",
  "received_at": "2026-10-04T06:34:03.562141Z",
  "assessed_at": "2026-10-04T06:34:03.878396Z",
  "updated_at": "2026-10-04T06:34:03.878396Z",
  "patient": {
    "id": "P-ANNA",
    "birth_date": "1974-03-12",
    "sex": "female"
  },
  "recommendations": [
    {
      "id": "28b9191c-c1f5-4987-9bad-00223872764a",
      "position": 1,
      "source": "ai",
      "service_code": "ONC-MAMMO-CONSULT",
      "service_name": "Консультация онколога-маммолога",
      "importance": "high",
      "rationale": "BI-RADS 4 — показана консультация специалиста и решение вопроса о биопсии.",
      "guideline_ref": "КР МЗ РФ «Рак молочной железы»",
      "patient_text": "Рекомендуем консультацию маммолога, чтобы обсудить результаты обследования и дальнейшие шаги.",
      "already_booked": false,
      "review": {
        "mark": "rejected",
        "reject_reason": "other",
        "reject_comment": "уже наблюдается у онколога",
        "reviewed_by": "dr-ivanova",
        "reviewed_at": "2026-10-04T07:10:00Z"
      }
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `patient.id` | ID пациента в МИС |
| `status` | `in_review` — на проверке, `confirmed` — врач подтвердил. Дальнейший путь пациента (уведомлён, записан, …) — в плане пациента и задачах администратора |
| `recommendations` | Отсортированы по `position`; пустой массив, если рекомендаций нет |
| `recommendations[].service_code` | `""` — услуги нет в клинике |
| `recommendations[].review` | `null`, пока врач не отметил рекомендацию; `reject_reason` и `reject_comment` есть только у отклонённых |

| Код | Когда |
|---|---|
| 200 | Кейс найден |
| 404 | Кейса нет, ai-service его ещё не оценил, или `id` не UUID |

## История приёмов пациента

`GET /api/v1/cases/{id}/history`

b2b-service запрашивает историю пациента кейса в МИС в момент вызова.

```json
{
  "visits": [
    { "service_code": "MG-SCREENING", "service_name": "Маммография (скрининг)", "visited_at": "2025-09-15T09:00:00Z" }
  ],
  "appointments": [
    { "service_code": "PULM-CONSULT", "service_name": "Консультация пульмонолога", "scheduled_at": "2026-10-05T06:00:00Z" }
  ]
}
```

| Код | Когда |
|---|---|
| 200 | История получена; массивы могут быть пустыми |
| 404 | Кейса нет |
| 502 | МИС недоступна или ответила ошибкой |

## Бизнес-время

`GET /api/v1/clock`

Текущее время сервиса с учётом демо-перемотки. Таймеры ожидания и SLA на фронте считаются от него, а не от часов браузера.

```json
{ "now": "2026-10-04T07:04:34.383389Z" }
```

## Проверка врачом

Все действия, кроме чтения очереди, требуют заголовок `X-User-ID`: без него — 401. Изменения возможны только пока кейс в статусе `in_review`, иначе — 409 с описанием текущего статуса.

### Очередь

`GET /api/v1/review/queue`

Кейсы в статусе `in_review`. Порядок: сначала по срочности (`emergency`, `priority`, `planned`, `normal`), внутри уровня — по времени поступления.

```json
{
  "cases": [
    {
      "case_id": "68b07f74-b201-4b05-b8ce-e969ea05b263",
      "urgency": "emergency",
      "modality": "DX",
      "performed_at": "2026-10-03T09:00:00Z",
      "received_at": "2026-10-04T06:34:03.601Z",
      "patient": { "id": "P-SERGEY", "full_name": "Сергей Иванов", "birth_date": "1988-07-20", "sex": "male" },
      "recommendations_total": 1,
      "recommendations_reviewed": 0,
      "opened_at": "2026-10-04T06:40:12Z"
    }
  ]
}
```

`opened_at` – когда врач впервые открыл кейс (`POST .../open`); поля нет, пока кейс не открывали.

### Врач открыл кейс

`POST /api/v1/cases/{id}/open`

Фиксирует в аудите, что врач взял кейс в работу. По этому событию будет строиться эскалация «врач не открыл неотложный кейс за 30 минут». Тело запроса не нужно, ответ без тела.

| Код | Когда |
|---|---|
| 204 | Событие записано |
| 401 | Нет `X-User-ID` |
| 404 | Кейса нет |
| 409 | Кейс не в `in_review` |

### Отметка рекомендации

`PATCH /api/v1/cases/{id}/recommendations/{rec_id}`

Частичное обновление: можно передать отметку, новый текст для пациента или и то и другое. Повторный вызов перезаписывает отметку. Текст можно править и до отметки: отметка при этом не меняется, в аудит пишется событие `recommendation_text_edited`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `mark` | `critical` \| `minor` \| `rejected` | если нет `patient_text` | Отметка врача |
| `reject_reason` | `contraindicated` \| `other` | для `rejected` | Причина отклонения; для других отметок не передаётся |
| `reject_comment` | string | для `other` | Комментарий к причине «другое» |
| `patient_text` | string | если нет `mark` | Исправленный текст для пациента; не передан — текст не меняется; пустая строка — 400 |

```json
{ "mark": "critical", "patient_text": "Пожалуйста, запишитесь к маммологу в ближайшие дни." }
```

Ответ 200 — рекомендация в том же виде, что в карточке кейса. `review` заполнен, если рекомендация уже отмечена.

| Код | Когда |
|---|---|
| 200 | Отметка сохранена |
| 400 | Нет ни `mark`, ни `patient_text`; недопустимая отметка или причина; причина у неотклонённой рекомендации; `other` без комментария; пустой `patient_text` |
| 401 | Нет `X-User-ID` |
| 404 | Кейса нет; рекомендация принадлежит другому кейсу или не входит в план — врач её отклонил |
| 409 | Кейс не в `in_review` |

### Своя рекомендация врача

`POST /api/v1/cases/{id}/recommendations`

Добавляется в конец списка со `source: "doctor"` и сразу считается отмеченной. `importance` выводится из отметки: `critical` → `high`, `minor` → `low`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `service_name` | string | да | Название услуги или специалиста |
| `patient_text` | string | да | Текст для пациента |
| `mark` | `critical` \| `minor` | да | Отметка врача |
| `service_code` | string | нет | Код услуги из каталога; без него услуга считается недоступной в клинике |
| `rationale` | string | нет | Обоснование для коллег |

```json
{
  "service_name": "Консультация онколога",
  "patient_text": "Рекомендуем консультацию онколога для обсуждения результатов.",
  "mark": "minor"
}
```

Ответ 201 — созданная рекомендация.

| Код | Когда |
|---|---|
| 201 | Рекомендация добавлена |
| 400 | Нет `service_name` или `patient_text`; `mark` не `critical`/`minor` |
| 401 | Нет `X-User-ID` |
| 404 | Кейса нет |
| 409 | Кейс не в `in_review` |

### Смена срочности

`PUT /api/v1/cases/{id}/urgency`

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `urgency` | `normal` \| `planned` \| `priority` \| `emergency` | да | Новый уровень |
| `reason` | string | при понижении | Причина; попадает в аудит |

```json
{ "urgency": "planned", "reason": "очаг стабилен по сравнению с прошлым КТ" }
```

| Код | Когда |
|---|---|
| 204 | Срочность изменена |
| 400 | Неизвестное значение; уровень не меняется; понижение без причины |
| 401 | Нет `X-User-ID` |
| 404 | Кейса нет |
| 409 | Кейс не в `in_review` |

### Подтверждение кейса

`POST /api/v1/cases/{id}/confirm`

Переводит кейс в `confirmed`. После этого рекомендации с отметками `critical` и `minor` становятся видны пациенту, а протокол ставит таймеры (см. [Протокол после подтверждения](#протокол-после-подтверждения)): в фоне сразу уходит уведомление пациенту и кейс переходит в `notified`. Тело запроса не нужно.

```json
{ "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f", "status": "confirmed" }
```

| Код | Когда |
|---|---|
| 200 | Кейс подтверждён |
| 401 | Нет `X-User-ID` |
| 404 | Кейса нет |
| 409 | Кейс не в `in_review`; есть неотмеченные рекомендации (их число в описании ошибки) |

Параллельные подтверждения одного кейса безопасны: успешным будет ровно одно, остальные получат 409.

## Для b2c-service

### План пациента

`GET /api/v1/patients/{external_id}/plan?source_system={source_system}`

Пациентская выборка: только то, что можно показывать пациенту.

- Кейсы в статусах `confirmed`, `notified`, `booked`, `completed`, `declined`, `unreachable` — с рекомендациями, которые врач отметил как `critical` или `minor`.
- Кейсы в `in_review` — без рекомендаций: пациенту показывается «Врач готовит ваш план». Неотложный кейс в `in_review`, `confirmed`, `notified` помечен `urgent_contact: true`.
- Кейсы в `received` (ai-service ещё не оценил) не попадают.

Кейсы отсортированы от новых исследований к старым.

```json
{
  "now": "2026-10-04T12:00:00Z",
  "patient": { "full_name": "Анна Смирнова" },
  "cases": [
    {
      "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
      "status": "notified",
      "urgent_contact": false,
      "no_findings": false,
      "confirmed_at": "2026-10-03T15:00:00Z",
      "book_by": "2026-10-10T15:00:00Z",
      "study": { "modality": "MG", "performed_at": "2026-10-03T09:00:00Z" },
      "recommendations": [
        {
          "id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5",
          "service_code": "US-BREAST",
          "service_name": "УЗИ молочных желез",
          "patient_text": "Ультразвуковое исследование поможет врачу получить больше информации.",
          "mark": "critical",
          "declined": false
        }
      ]
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `now` | Бизнес-время сервиса: от него считаются «сегодня» и просрочки |
| `no_findings` | Срочность `normal`: «отклонений не найдено», рекомендация — плановый контроль |
| `confirmed_at` | Когда врач подтвердил; `null` у кейса на проверке |
| `book_by` | Записаться не позднее (см. [протокол](#протокол-после-подтверждения)); только у подтверждённых кейсов |
| `recommendations[].declined`, `decline_reason` | Пациент отказался от шага |

| Код | Когда |
|---|---|
| 200 | План найден; `cases` может быть пустым |
| 400 | Нет `source_system` |
| 404 | Пациент неизвестен b2b-service |

### Пациент не будет записываться

`POST /api/v1/cases/{id}/recommendations/{rec_id}/decline`

```json
{ "reason": "expensive", "comment": "" }
```

Отмечает отказ от шага с причиной. Если в кейсе не осталось шагов без записи и без отказа, кейс переходит в `declined`, таймеры протокола снимаются, а активная задача администратора закрывается со статусом `declined`. Причины отказов пациентов попадают в дашборд вместе с отказами, записанными администраторами.

```json
{ "recommendation_id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5", "case_status": "notified" }
```

| Код | Когда |
|---|---|
| 200 | Отказ записан; `case_status` — статус кейса после этого |
| 400 | Неизвестный `reason`; `other` без `comment` |
| 404 | Кейса нет или рекомендации нет в плане |
| 409 | Кейс ещё на проверке; по шагу уже есть запись; отказ уже записан |

### Пациент просит перезвонить

`POST /api/v1/cases/{id}/help-requests`

Создаёт задачу администратору с причиной `help_request` и сроком 2 часа. Если у кейса уже есть активная задача, новая не создаётся: в ответе существующая.

```json
{ "task_id": "4f0f7a1e-3d5b-4c55-9a52-0b8f0a3e1d10", "created": true }
```

| Код | Когда |
|---|---|
| 201 | Задача создана |
| 200 | У кейса уже есть активная задача |
| 404 | Кейса нет |

### Регистрация записи

`POST /api/v1/cases/{id}/bookings`

Сообщает b2b-service, что пациент записан в МИС по рекомендации. Кейс переходит в `booked`, если ещё не там, — в том числе из `declined` и `unreachable`: пациент передумал или сам дозвонился. Канал записи сохраняется для дашборда. Новая запись снимает таймеры протокола и закрывает активную задачу администратора со статусом `booked`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `recommendation_id` | UUID | да | Рекомендация кейса, по которой записан пациент |
| `appointment_id` | string | да | ID записи в МИС; ключ идемпотентности |
| `scheduled_at` | RFC 3339 | да | Время приёма |
| `channel` | `self` \| `operator` | да | Кто записал |

```json
{
  "recommendation_id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5",
  "appointment_id": "APT-0001",
  "scheduled_at": "2026-10-05T09:00:00+03:00",
  "channel": "self"
}
```

```json
{
  "booking_id": "0d3c9a6e-4b7e-4f53-9a2f-1f3f6f1c2b11",
  "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
  "recommendation_id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5",
  "appointment_id": "APT-0001",
  "case_status": "booked"
}
```

| Код | Когда |
|---|---|
| 201 | Запись зарегистрирована |
| 200 | Запись с этим `appointment_id` уже зарегистрирована для той же рекомендации |
| 400 | Нет обязательного поля; `recommendation_id` не UUID; `scheduled_at` не RFC 3339; неизвестный `channel` |
| 404 | Кейса нет; рекомендация принадлежит другому кейсу или не входит в план — врач её отклонил |
| 409 | Кейс ещё на проверке у врача или уже `completed`; услуги нет в клинике; `appointment_id` уже привязан к другой рекомендации |

## Протокол после подтверждения

Таймеры считаются по бизнес-времени, поэтому их можно проматывать демо-кнопками. Каждый таймер перед срабатыванием проверяет состояние кейса и ничего не делает, если пациент уже записался или кейс закрыт.

| Когда | Что происходит |
|---|---|
| ai-service вернул `emergency`, или врач поднял срочность до `emergency` | Задача администратору «неотложный случай» со сроком 1 час; пациенту push и SMS «срочно свяжитесь с клиникой» |
| Неотложный кейс + 30 минут, врач не открыл кейс | Уведомление дежурному врачу (`review_escalation`) |
| Неотложный кейс + 2 часа, задача не закрыта и не переведена в «перезвонить» | Уведомление дежурному администратору (`contact_escalation`) |
| Врач понизил срочность с `emergency` | Неотложные таймеры отменяются, задача закрывается со статусом `cancelled` |
| Подтверждение кейса | Сразу: уведомление пациенту, кейс → `notified`. `priority` — push и SMS, `normal` — «отклонений не найдено», остальные — push |
| `priority` + 1 день без записи | Задача администратору «не записался вовремя», срок 4 часа |
| `planned` + 3 и + 7 дней без записи | Напоминания пациенту |
| `planned` + 7 дней без записи | Задача администратору, срок 2 рабочих дня |
| Запись пациента или администратора | Все таймеры кейса отменяются, активная задача закрывается со статусом `booked` |

Срок «записаться не позднее» (`book_by`) считается от подтверждения: `emergency` — сегодня, `priority` — 7 дней, `planned` — 30 дней, `normal` — год.

Уведомления в MVP никуда не отправляются, а пишутся в журнал. Тексты пациенту не содержат диагнозов и находок.

## Администратор

Администратор не видит текст заключения и обоснования — только что предложить пациенту. Действия требуют `X-User-ID` с идентификатором администратора: он попадает в историю попыток и аудит. Активная задача у кейса одна.

### Список «Позвонить»

`GET /api/v1/operator/tasks[?mine=true]`

Активные задачи (`new`, `in_progress`, `no_answer`, `callback`). `mine=true` оставляет задачи текущего администратора и требует `X-User-ID`. Порядок: неотложные, затем просроченные, затем по сроку.

```json
{
  "tasks": [
    {
      "task": {
        "id": "4f0f7a1e-3d5b-4c55-9a52-0b8f0a3e1d10",
        "case_id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
        "reason": "no_booking",
        "status": "no_answer",
        "assignee": "admin-1",
        "due_at": "2026-10-05T13:00:00Z",
        "next_call_at": "2026-10-05T11:00:00Z",
        "attempts": 1,
        "needs_doctor": false,
        "created_at": "2026-10-05T09:00:00Z",
        "closed_at": null
      },
      "case": {
        "id": "6b9a5672-0028-4a5e-896e-defdef2ebf8f",
        "status": "notified",
        "urgency": "priority",
        "modality": "CT",
        "book_by": "2026-10-11T09:00:00Z"
      },
      "patient": { "id": "P-1002", "full_name": "Игорь Петров", "phone": "+7 916 000-00-02" },
      "offer_service": "Консультация пульмонолога"
    }
  ]
}
```

- `reason`: `emergency` — неотложный случай, `no_booking` — не записался вовремя, `help_request` — пациент просит перезвонить.
- `needs_doctor`: три попытки без ответа — метка «Передать врачу».
- `offer_service`: первая незаписанная услуга, `critical` раньше `minor`; пусто, пока врач не подтвердил кейс.

| Код | Когда |
|---|---|
| 200 | Список, может быть пустым |
| 401 | `mine=true` без `X-User-ID` |

### Карточка звонка

`GET /api/v1/operator/tasks/{id}`

Задача, кейс и пациент — как в списке, плюс история попыток и что предложить с ближайшими слотами из МИС. Доступна и для закрытой задачи.

```json
{
  "task": { "...": "как в списке" },
  "case": { "...": "как в списке" },
  "patient": { "...": "как в списке" },
  "attempts": [
    {
      "id": "c3a9d2f4-1b0e-4f7a-9b8c-2d1e0f3a4b5c",
      "outcome": "no_answer",
      "comment": "",
      "callback_at": null,
      "actor": "admin-1",
      "created_at": "2026-10-05T09:05:00Z"
    }
  ],
  "offers": [
    {
      "recommendation_id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5",
      "service_code": "PULM-CONSULT",
      "service_name": "Консультация пульмонолога",
      "patient_text": "Рекомендуем консультацию пульмонолога.",
      "mark": "critical",
      "booked": false,
      "slots": [{ "id": "PULM-CONSULT.202610060900", "starts_at": "2026-10-06T09:00:00+03:00" }],
      "slots_unavailable": false
    }
  ]
}
```

- `offers`: рекомендации с отметками `critical` и `minor`, сначала `critical`. Пусто, пока врач не подтвердил кейс.
- `slots` запрашиваются только для незаписанных услуг, которые есть в клинике, начиная с бизнес-времени b2b-service. Если МИС не ответила — `slots: []` и `slots_unavailable: true`, карточка всё равно открывается.

| Код | Когда |
|---|---|
| 200 | Карточка |
| 404 | Задачи нет |

### Действия

Все действия — `POST /api/v1/operator/tasks/{id}/{action}` с `X-User-ID`. Тело необязательно, если в таблице не сказано иное; `comment` принимают все действия. Ответ — задача в формате списка (поле `task`).

| Действие | Тело | Что делает |
|---|---|---|
| `take` | — | `in_progress`, задача назначается администратору |
| `no-answer` | `{"comment"}` | `no_answer`, `attempts` + 1, повторный звонок через 15 минут для неотложных и 2 часа для остальных. На третьей попытке пациенту уходит SMS «не смогли дозвониться», кейс → `unreachable` (если был `confirmed` или `notified`), в задаче появляется `needs_doctor` |
| `callback` | `{"call_at", "comment"}` | `callback`, `next_call_at = call_at`. `call_at` обязателен, RFC 3339, в будущем |
| `contacted` | `{"comment"}` | Дозвонился, закрыть задачу: `contacted` |
| `decline` | `{"reason", "comment"}` | Задача `declined`, кейс → `declined`, таймеры снимаются. `reason` обязателен; для `other` обязателен `comment` |
| `hand-to-doctor` | `{"comment"}` | Задача `handed_to_doctor`, уведомление дежурному врачу с комментарием |

| Код | Когда |
|---|---|
| 200 | Действие выполнено |
| 400 | Нет или некорректно `call_at`; `call_at` не в будущем; неизвестный `reason`; `other` без `comment` |
| 401 | Нет `X-User-ID` |
| 404 | Задачи нет |
| 409 | Задача уже закрыта |

### Запись администратором

`POST /api/v1/operator/tasks/{id}/bookings`

b2b-service записывает пациента в МИС на выбранный слот, регистрирует запись с каналом `operator` и закрывает задачу со статусом `booked`. Повтор с тем же слотом безопасен: МИС вернёт ту же запись.

```json
{
  "recommendation_id": "ebc65e72-26b8-4e68-ace0-63f164a3cce5",
  "slot_id": "PULM-CONSULT.202610060900",
  "comment": "удобно утром"
}
```

Ответ — как у [регистрации записи](#регистрация-записи).

| Код | Когда |
|---|---|
| 201 | Записан |
| 400 | `recommendation_id` не UUID; нет `slot_id`; МИС не принимает слот |
| 401 | Нет `X-User-ID` |
| 404 | Задачи или рекомендации нет |
| 409 | Задача закрыта; рекомендация не подтверждена врачом или услуги нет в клинике; слот занят |
| 502 | МИС недоступна |

## Руководитель

### Дашборд

`GET /api/v1/dashboard?days={1..365}`

Воронка, разрезы, SLA и причины отказов за последние `days` календарных дней по бизнес-времени: с полуночи UTC `days − 1` дней назад до текущего момента. Прошлый период — столько же дней перед ним.

```json
{
  "period": { "from": "2026-09-06T00:00:00Z", "to": "2026-10-05T19:30:00Z", "days": 30 },
  "previous_period": { "from": "2026-08-07T00:00:00Z", "to": "2026-09-06T00:00:00Z", "days": 30 },
  "current": {
    "funnel": { "received": 278, "recommended": 152, "confirmed": 151, "notified": 151, "booked": 97, "completed": 66 },
    "doctor_sla": { "on_time": 253, "total": 278 },
    "operator_sla": { "on_time": 70, "total": 89 },
    "bookings": { "self": 69, "operator": 28 }
  },
  "previous": { "...": "те же поля" },
  "by_urgency": [
    {
      "urgency": "priority",
      "confirmed": 75,
      "booked": 51,
      "doctor_sla": { "on_time": 63, "total": 75 },
      "operator_sla": { "on_time": 22, "total": 39 }
    }
  ],
  "by_modality": [{ "modality": "CT", "confirmed": 64, "booked": 34 }],
  "decline_reasons": [{ "reason": "other_clinic", "count": 8 }],
  "trend_step": "day",
  "trend": [{ "from": "2026-09-06T00:00:00Z", "received": 12, "booked": 5 }]
}
```

**Воронка** — кейсы, поступившие за период; каждый шаг — подмножество предыдущего:

| Шаг | Кейс засчитан, если |
|---|---|
| `received` | поступил за период |
| `recommended` | ai-service оценил его срочность выше `normal`: есть находка и рекомендации к дообследованию. «Норма» с напоминанием о скрининге сюда не входит |
| `confirmed` | врач подтвердил кейс и оставил хотя бы одну рекомендацию `critical` или `minor` |
| `notified` | пациент уведомлён |
| `booked` | есть запись по рекомендации; `bookings` делит записи по каналу первой записи |
| `completed` | пациент пришёл. В MVP факт визита из МИС не приходит, шаг заполняется только демо-историей |

**Сравнение с прошлым периодом честное:** `previous` считается по состоянию на конец прошлого периода, а `current` — на текущий момент. У свежих кейсов было одинаково мало времени дойти до записи, поэтому разница отражает изменение, а не «незрелость» последних дней.

**SLA** — доля выполненных вовремя; незавершённое с истёкшим сроком считается нарушением, незавершённое в срок не учитывается:

- `doctor_sla` — кейсы периода: от оценки ai-service до подтверждения врачом. Срок: `emergency` 30 минут, `priority` 4 часа, `planned` и `normal` 24 часа.
- `operator_sla` — задачи администратора, созданные за период: закрыта до `due_at`. Задачи, снятые протоколом (`cancelled`), не учитываются.

**Разрезы** `by_urgency` и `by_modality` — по текущему периоду: `confirmed` и `booked` как в воронке. Порядок срочностей: `emergency`, `priority`, `planned`, `normal`; у `normal` осмысленно только `doctor_sla`.

**`decline_reasons`** — отказы за период по убыванию: записанные администраторами и отмеченные самими пациентами.

**`trend`** — по датам событий: `received` — поступившие в этот день, `booked` — записавшиеся в этот день (по первой записи кейса). Шаг — день, а для периода длиннее 31 дня — неделя (`trend_step: "week"`); последняя точка может быть неполной.

| Код | Когда |
|---|---|
| 200 | Дашборд |
| 400 | `days` не число от 1 до 365 |

## Демо

Ручки доступны только при `DEMO_MODE=true`, иначе 404.

### Перемотка времени

`POST /demo/clock/advance`

Сдвигает бизнес-время сервиса вперёд: таймеры, время поступления и событий считаются от сдвинутых часов. Сдвиг хранится в памяти и сбрасывается при перезапуске.

```json
{ "by": "30m" }
```

```json
{ "now": "2026-10-04T07:04:34.383389Z" }
```

| Код | Когда |
|---|---|
| 200 | Время сдвинуто; в ответе текущее бизнес-время |
| 400 | `by` не положительная длительность Go (`30m`, `24h`, `1h30m`) |

### Сброс демо

`POST /demo/reset`

Удаляет все данные сервиса (пациенты, кейсы, рекомендации, события, фоновые задачи, задачи администратора, уведомления, записи), возвращает бизнес-время к текущему и наполняет базу синтетической историей для дашборда. Тело запроса не нужно. Ответ 204.

История — около 1700 кейсов за 180 дней до текущего момента с `source_system = "demo-history"`. Генератор детерминирован (фиксированное зерно) и проводит каждый кейс через настоящие переходы: оценка, проверка врачом, уведомление, запись сам или через администратора, отказы, недозвоны, визиты. Последние 12 часов истории пусты, а всё, что случилось бы позже текущего момента, отбрасывается. Поэтому история не попадает в очередь врача, список «Позвонить», журнал уведомлений и B2C. Записи в mis-demo сбрасываются отдельно – `POST mis-demo /demo/reset`.
